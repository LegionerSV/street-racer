# Архитектура предварительно подготовленных тайлов карты в S3

## 1. Цель документа

Нужно ускорить запуск игры и фоновую подгрузку карты без обязательного
серверного приложения.

На первом этапе Москва и Санкт-Петербург заранее подготавливаются локально и
публикуются в Yandex Object Storage. Во время игры клиент сначала ищет тайл в
локальном кэше браузера, затем в S3 и только при отсутствии готового файла
использует существующую схему загрузки через Overpass и источник рельефа.

Целевая цепочка источников:

```text
IndexedDB
  -> Yandex Object Storage
    -> Overpass + DEM
```

В первой поставке сервер и виртуальная машина не требуются. Бакет содержит
публичные неизменяемые файлы карты и манифест опубликованного набора.

Документ также описывает следующий независимый этап: инкрементальное добавление
данных в игровой мир без полной перестройки всего удерживаемого окна карты.

## 2. Текущее состояние

Основные части текущей реализации:

- [`game/region-stream.ts`](../game/region-stream.ts) делит мир на клетки по
  1 км относительно выбранной стартовой координаты, загружает начальные четыре
  клетки и затем поддерживает скользящее окно.
- [`game/map-source.ts`](../game/map-source.ts) получает OSM-объекты через
  публичные Overpass API, дробит тяжёлые запросы и сохраняет ответы в IndexedDB.
- [`game/data.ts`](../game/data.ts) загружает и кэширует DEM, а также содержит
  существующий доступ к IndexedDB.
- [`game/network.ts`](../game/network.ts) преобразует объединённый `RegionData`
  в полный `World`.
- [`game/world.worker.ts`](../game/world.worker.ts) при каждом обновлении вызывает
  `buildWorld` для всего удерживаемого набора данных, готовит новую версию мира и
  переключает её по `commit`.
- [`game/runtime.ts`](../game/runtime.ts) после переключения мира определяет
  изменившиеся игровые chunks, переносит трафик и постепенно перестраивает
  геометрию.
- [`game/chunks.ts`](../game/chunks.ts) строит геометрию и физику кварталов
  размером 250 м.
- [`game/world-update.ts`](../game/world-update.ts) сопоставляет старый и новый
  мир и определяет затронутые chunks.
- [`game/stream-coverage.ts`](../game/stream-coverage.ts) трактует текущее
  покрытие как относительные километровые клетки.
- [`docs/map-streaming.md`](map-streaming.md) документирует существующее
  поведение и ограничения стриминга.

Холодный старт сейчас требует до 16 последовательных запросов частей OSM для
четырёх стартовых клеток, отдельного определения стороны движения и загрузки
рельефа. После добавления новой клетки worker снова строит весь `World`. Поэтому
есть две независимые задачи:

1. убрать ожидание публичного Overpass там, где карта заранее подготовлена;
2. убрать полную перестройку мира при фоновой подгрузке.

Первую задачу следует закончить и выпустить отдельно. Она не должна зависеть от
готовности инкрементального обновления мира.

## 3. Принятые архитектурные решения

### 3.1. Глобальная сетка XYZ

Source-тайлы идентифицируются стандартным ключом Web Mercator `z/x/y`.
Начальное значение масштаба — `z = 15`.

Причины выбора:

- алгоритм не зависит от стартовой координаты игрока;
- одинаковая точка всегда попадает в одинаковый тайл;
- границы тайлов однозначны и совместимы с обычными картографическими
  инструментами;
- структура естественно отображается на ключи S3;
- для Москвы один тайл имеет ширину примерно 690 м по поверхности, для
  Санкт-Петербурга — примерно 610 м, что даёт умеренный размер исходных данных.

QuadKey не используется как основной идентификатор. При необходимости его можно
получить из тех же `z/x/y`, но путь `z/x/y` проще читать и диагностировать.

Web Mercator ограничивается широтой примерно `±85.05112878`. Существующее
ограничение выбора игровой координаты должно быть согласовано с этим пределом.

### 3.2. Source-тайл и игровой chunk — разные сущности

`SourceTile` содержит географические исходные данные. Его размер определяется
сеткой XYZ и меняется в метрах с широтой.

`GameChunk` остаётся локальным квадратом 250 × 250 м. Он содержит меши,
коллизии, растительность, разметку и другие объекты сцены.

Нельзя использовать один строковый ключ без указания его системы координат.
Типы и API должны различать:

```text
SourceTileId: z/x/y
GameChunkKey: localX/localZ
```

Готовность игрового chunk определяется географическим покрытием всех
source-тайлов, пересекающих необходимую область chunk, а не делением локального
ключа на четыре.

### 3.3. Окно задаётся метрами, а не фиксированным числом тайлов

Вместо постоянного окна 10 × 10 задаются физические радиусы:

- блокирующее покрытие при старте: 800–1000 м от автомобиля;
- целевое удерживаемое покрытие: 2500–3000 м;
- упреждающее покрытие по направлению движения: ещё 1–2 ряда source-тайлов;
- область под автомобилем и критические chunks всегда закреплены и не могут
  быть вытеснены.

Для Москвы и Санкт-Петербурга целевое окно обычно получится около 9 × 9 или
11 × 11 тайлов. Нечётная сторона удобнее: текущий тайл находится в центре.

Игра не должна ждать всё целевое окно. Сначала загружается минимальная безопасная
область, затем остальное загружается в фоне по приоритету расстояния и направления
движения. Существующие бюджеты количества OSM-объектов и памяти сохраняются.

### 3.4. Первый формат содержит семантические данные, а не готовые меши

Первая версия S3-артефакта должна быть близка к существующему `MapTile`:

```text
TileArtifactV1
  schemaVersion
  tileBuildVersion
  z, x, y
  coreBounds
  bufferedBounds
  generatedAt
  osmTimestamp
  drivingSide
  elements
  elevation
  checksum
```

Тайл содержит OSM-объекты и рельеф, достаточные для существующего `buildWorld`.
Готовые Babylon-меши в первой версии не сохраняются, потому что они сильнее
привязаны к версии рендера, тяжелее и сложнее проверяются.

Координаты артефакта не должны зависеть от точки старта игровой сессии:

- OSM хранится в `lat/lon`;
- DEM содержит однозначную географическую привязку сетки;
- перевод в локальные игровые `x/z` выполняется относительно центра текущей
  сессии после загрузки.

В первой реализации допустим JSON, сжатый Brotli или gzip. Для `Float32Array`
нужно определить однозначное представление и восстановление типа после JSON.
Переход на MessagePack, CBOR или собственный бинарный контейнер выполняется
только после измерения размеров и времени разбора JSON-варианта.

### 3.5. Core и halo

Каждый source-тайл имеет:

- `coreBounds` — точные границы XYZ;
- `bufferedBounds` — область с запасом вокруг core.

Начальный размер halo — 300 м, как в текущем стриминге. В артефакт включаются
зависимые узлы, отношения и геометрия объектов, пересекающих buffered bounds.

После объединения соседних тайлов объекты дедуплицируются по ключу
`type/osmId`. Удаление тайла из памяти не удаляет объект, пока тот присутствует
хотя бы в одном другом удерживаемом тайле.

### 3.6. Источники взаимозаменяемы

Нужен интерфейс наподобие:

```text
TileSource.load(tileId, signal) -> TileLoadResult
```

Результат должен различать:

- успешное получение тайла;
- известное отсутствие (`404` или отсутствие в манифесте);
- временную ошибку;
- несовместимую версию;
- повреждённый артефакт;
- отмену операции.

Цепочка источников:

1. `IndexedDbTileSource`;
2. `S3TileSource`;
3. `OverpassTileSource` с существующим DEM.

Fallback обязан создавать тот же `TileArtifactV1`, что и офлайн-генератор.
После fallback результат сохраняется только в IndexedDB. Клиент никогда не
получает ключи записи в S3 и не загружает файлы в бакет.

### 3.7. Публичный S3 без секретов в клиенте

Бакет или отдельный префикс должен разрешать публичное чтение готовых тайлов и
манифеста. Для домена игры настраивается CORS с методами `GET` и при необходимости
`HEAD` для диагностики.

В штатной загрузке отдельный `HEAD` перед `GET` не выполняется. Если манифест
сообщает о наличии тайла, сразу выполняется `GET`. Без манифеста `GET` с ответом
`404` означает переход к fallback.

Адрес бакета задаётся конфигурацией сборки, например
`VITE_MAP_TILE_BASE_URL`. Отсутствующая настройка полностью отключает S3 и
сохраняет прежнее поведение.

### 3.8. Версионирование и атомарная публикация

Следует разделить:

- `schemaVersion` — формат файла;
- `tileBuildVersion` — версия алгоритмов подготовки геоданных;
- `datasetId` — конкретный снимок опубликованных данных.

Пример структуры:

```text
maps/catalog-v1.json
maps/v1/{tileBuildVersion}/{datasetId}/15/{x}/{y}.tile.json.br
```

`catalog-v1.json` содержит активные наборы, список или компактный индекс тайлов,
размеры, контрольные суммы и дату данных OSM. Все файлы набора неизменяемы и
получают долгий `Cache-Control`. Каталог публикуется последним, после загрузки и
проверки всех тайлов. Это атомарно переключает клиента на новый набор.

Текущий [`game/map-version.ts`](../game/map-version.ts) остаётся версией полного
игрового расчёта. Для S3 вводятся отдельные версии, чтобы косметическое изменение
рендера не требовало повторной публикации всех исходных тайлов.

## 4. Целевая схема первой поставки

```text
Выбранная координата
  -> вычисление центрального XYZ z15
  -> планирование безопасного и фонового окна
  -> для каждого тайла:
       IndexedDB
         -> S3 по опубликованному каталогу
           -> Overpass + DEM
  -> объединение и дедупликация TileArtifactV1
  -> существующий buildWorld
  -> существующий prepare/commit
  -> перестройка затронутых GameChunk 250 м
```

Эта поставка ускоряет Москву и Санкт-Петербург, но ещё не устраняет полностью
локальную стоимость `buildWorld` и переключения мира.

## 5. Целевая схема инкрементального обновления

Текущий полный снимок заменяется патчем:

```text
TileArtifact загружен
  -> worker.addSourceTile(tile)
  -> обновление реестра исходных объектов
  -> перестройка tile + halo или ограниченного блока соседей
  -> WorldPatch
  -> инвалидирование только dirty GameChunk
  -> атомарная установка критических коллизий
  -> фоновая установка дальних мешей с кадровым бюджетом
```

Предлагаемый состав `WorldPatch`:

```text
WorldPatch
  coverageAdded
  coverageRemoved
  nodesAddedOrUpdated
  nodesRemoved
  edgesAddedOrUpdated
  edgesRemoved
  restrictionsAddedOrUpdated
  restrictionsRemoved
  buildingsAddedOrUpdated
  buildingsRemoved
  areasAddedOrUpdated
  areasRemoved
  elevationPatches
  dirtyChunks
  invalidatedRoutes
```

Первый инкрементальный вариант может перестраивать блок 3 × 3 source-тайла
вокруг изменения. Это проще и безопаснее точечной модификации отдельных OSM
объектов, но всё равно существенно дешевле полной перестройки окна.

Для реализации потребуются стабильные идентификаторы дорожных рёбер. Ссылки
трафика, маршрутов и безопасной позиции нельзя хранить только как индексы массива.
Базовый ключ ребра: `way/from/to/direction`, дополненный при необходимости
идентификатором сегмента.

Worker должен хранить двусторонний реестр:

```text
source tile -> OSM objects
OSM object -> source tiles / reference count
```

При commit кэш геометрии worker-а больше не сбрасывается полностью. Удаляются
только записи `chunkKey/lod`, вошедшие в `dirtyChunks`.

## 6. Стратегия локальной подготовки Москвы и Санкт-Петербурга

Нельзя готовить два города тысячами запросов к публичным Overpass API.

Локальный конвейер должен:

1. получить региональный `.osm.pbf` из легального источника выгрузок OSM;
2. вырезать заданные полигоны Москвы и Санкт-Петербурга;
3. построить или использовать локальный пространственный индекс;
4. получить список XYZ z15, пересекающих полигоны;
5. для каждого тайла извлечь core + halo и полные зависимости объектов;
6. получить и локально закэшировать необходимые исходные DEM-тайлы;
7. создать `TileArtifactV1` общей библиотекой проекта;
8. проверить границы, типы, контрольную сумму и максимальный размер;
9. записать результат в staging-каталог;
10. возобновлять обработку после сбоя, пропуская валидные готовые файлы;
11. загрузить неизменяемые файлы в S3;
12. проверить несколько загруженных файлов чтением из S3;
13. опубликовать каталог последним.

Сначала создаётся пилотный набор:

- 10 × 10 тайлов центра Москвы;
- 10 × 10 тайлов центра Санкт-Петербурга;
- несколько окраинных тайлов;
- клетки с мостами, тоннелями, водой, сложными развязками и плотной
  застройкой.

До генерации полного покрытия измеряются:

- средний, p95 и максимальный размер сжатого и распакованного тайла;
- число OSM-объектов;
- время извлечения, сериализации и проверки;
- время скачивания и разбора в браузере;
- стоимость полного `buildWorld`;
- количество дубликатов из halo;
- размер IndexedDB и heap после удержания рабочего окна.

## 7. Наблюдаемость

В журнал загрузки и диагностику добавляются:

- `tileId`;
- источник: `indexeddb`, `s3`, `overpass`;
- результат обращения к каждому источнику;
- размер сжатого ответа, если доступен;
- размер распакованных данных;
- время сети, разбора, валидации и сохранения;
- причина fallback;
- число активных и удерживаемых source-тайлов;
- число входных OSM-объектов после дедупликации;
- время `buildWorld`, `prepare`, `commit` и установки chunks;
- количество dirty chunks;
- задержка кадра во время применения обновления.

Без этих метрик нельзя определить, закончилась ли сетевая проблема и какой объём
оставшихся пауз создаёт локальная перестройка.

## 8. Требования к совместимости и безопасности

- Если S3 не настроен или недоступен, игра должна работать по старой схеме.
- Ошибка одного фонового тайла не должна завершать игровую сессию.
- Отмена старта должна отменять S3, IndexedDB, Overpass и DEM-запросы.
- Повреждённый или несовместимый тайл не считается готовым.
- Тайл не устанавливается, если после сетевого ожидания он больше не входит в
  актуальное окно игрока и не закреплён критической областью.
- Нельзя удалять данные под автомобилем до установки замены.
- Публичный клиент не содержит секретов Yandex Cloud.
- Публикация и документация сохраняют обязательную атрибуцию OpenStreetMap и
  учитывают требования ODbL к производной базе данных.
- Все текстовые файлы сохраняются в UTF-8.

Результат: все новые запросы используют детерминированные XYZ-тайлы, но получают

### Поставка B — чтение из S3

Результат: клиент использует цепочку IndexedDB → S3 → fallback. Бакет может быть
пустым, поведение игры не ухудшается.

### Поставка C — локальный генератор и пилот

Результат: в S3 опубликованы тестовые наборы Москвы и Санкт-Петербурга, собраны
метрики формата и загрузки.

### Поставка D — полное покрытие двух городов

Результат: выбранные полигоны полностью подготовлены, проверены и опубликованы.

### Поставка E — инкрементальный WorldPatch

Результат: добавление source-тайла не вызывает полный `buildWorld` удерживаемого
окна и не сбрасывает весь кэш геометрии.

> `tile -> objects` и обратные reference counts, принимать add/remove source tile
> и возвращать типизированный `WorldPatch`. В первой реализации разрешается
> перестраивать область 3 × 3 source-тайла вокруг изменения, но запрещается
> вызывать полный `buildWorld` для всего удерживаемого окна. Halo, длинные дороги,
> мосты, ограничения поворотов, здания и DEM должны расширять dirty bounds до
> фактически затронутой области. Сохрани двухфазную prepare/commit семантику для
> безопасной установки около автомобиля. Удаление source-тайла не удаляет OSM
> object, пока его reference count больше нуля.

**Критерии приёмки:**

- добавление одного тайла не строит весь удерживаемый мир;
- неизменившиеся стабильные сущности сохраняют ID;
- объекты halo корректно дедуплицируются и удаляются по reference count;
- `WorldPatch` содержит точный список dirty chunks;
- ошибки prepare не повреждают активный мир;
- тесты покрывают мост через несколько тайлов, ограничение поворота, DEM-шов,
  добавление и удаление клетки;
- `npm test`, `npm run typecheck`, `npm run lint` и `npm run build:pages`
  проходят.

### MAP-S3-14. Применять WorldPatch без полного сброса сцены и кэша

**Зависимости:** MAP-S3-13.

**Задание агенту:**

> Интегрируй `WorldPatch` в [`game/runtime.ts`](../game/runtime.ts),
> [`game/chunks.ts`](../game/chunks.ts), [`game/traffic.ts`](../game/traffic.ts) и
> связанные системы. При commit инвалидируй только `dirtyChunks` и соответствующие
> записи `chunkKey/lod`; не сбрасывай весь worker cache. Критические chunks под
> машиной и впереди должны получить новые коллизии атомарно до разблокировки
> управления. Дальние меши устанавливай постепенно с измеряемым кадровым
> бюджетом, начальное значение 2–4 мс за кадр. Трафик переносится по стабильным
> edge ID и пересчитывается только при затрагивании его дороги. Маршруты гонок
> инвалидируются только при изменении их покрытия или рёбер. Добавь метрики
> prepare, commit, dirty count, install time и максимальной задержки кадра.

**Критерии приёмки:**

- неизменившиеся chunks не перестраиваются;
- кэш геометрии не очищается целиком;
- машина не проваливается и не получает управление до готовности критических
  коллизий;
- фоновая установка не создаёт длинного синхронного цикла в одном кадре;
- трафик и активная гонка соблюдают существующие правила блокировки обновления;
- долгий тест поездки подтверждает ограниченную память и отсутствие полной
  перестройки;
- `npm test`, `npm run typecheck`, `npm run lint` и `npm run build:pages`
  проходят.

## 11. Общие команды проверки для задач

Минимальный набор после изменений TypeScript:

```powershell
npm test

npm run lint
```

Для задач, меняющих сборку, runtime, worker или публичную конфигурацию:

```powershell

```

Перед завершением каждой задачи необходимо выполнить установленную проектом
проверку mojibake сначала в режиме `-WhatIf`, затем применять исправление только
если список кандидатов действительно корректен.

## 12. Критерий завершения инициативы

Инициатива считается завершённой, когда:

- Москва и Санкт-Петербург загружаются из S3 без Overpass при холодном старте;
- отсутствие S3-тайла прозрачно возвращает существующий fallback;
- две близкие точки старта разделяют одни и те же source-тайлы;
- окно выбирается по физическому радиусу, а не по жёсткому числу клеток;
- память ограничена при длительной поездке;
- швы дорог, зданий и рельефа проходят автоматические и визуальные проверки;
- добавление source-тайла не перестраивает весь удерживаемый мир;
- критические коллизии устанавливаются безопасно, а дальняя геометрия — без
  заметного длинного кадра;
- опубликованный dataset версионирован, проверяем и допускает откат;
- клиент не содержит секретов облачного хранилища.
